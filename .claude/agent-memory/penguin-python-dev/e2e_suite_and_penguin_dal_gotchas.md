**`tests/e2e/` now has a real pytest suite** (branch `feature/e2e-suite`, off `release/v0.2.X`) alongside the pre-existing Playwright JS suite (`tests/e2e/tests/smoke.spec.js`, unrelated, webui-only). `tests/e2e/conftest.py` boots the real proxy service as a hypercorn subprocess (`WADDLEAI_STUB_UPSTREAM=1`), same pattern as `tests/contract/conftest.py` but drives multi-request flows through real HTTP rather than golden-snapshotting single endpoints. Fixtures: `proxy_process` (default, no cache/routing flags), `routing_proxy` (smart_routing on, isolated), `cache_proxy` + `docker_redis` (response_cache on + real redis container, currently unusable — see below). `seed_org`/`open_db` factory fixtures let a test seed a second org or query the DB directly against an already-running proxy's sqlite file.

**Systemic bug found + partially fixed: `.update_record()` is not a penguin_dal API.** `penguin_dal.query.Row` (packages/python-dal/src/penguin_dal/query.py) has no `update_record` method — that's classic PyDAL. The correct call is `db(condition).update(**kwargs)` on a `QuerySet`. Every `.update_record()` call site silently raised `AttributeError`, caught by a broad `except Exception` somewhere upstream (route handler → 500, or `OIDCAuthMiddleware`'s api-key-verifier exception handler → generic 401 "API key verification failed", masking the real cause). **Fixed** (writing the e2e suite required it): `shared/auth/rbac.py:202` (`authenticate_api_key`'s `last_used` update — this one broke ALL wa-/x-api-key auth, any key, any org, unconditionally, since a bcrypt match always hit this line next) and `shared/utils/token_manager.py` (3 sites in `_update_usage_records`/`_update_usage_cache` — broke usage accounting for the *second* request per api_key per calendar day). **Still broken, not fixed (flagged only):** `services/management/app/api/v1/memory_config.py` (×3), `services/management/app/api/v1/memory_scoping.py` (×1), `shared/utils/metering.py` (×1) — same bug, different call sites, out of scope for the e2e-suite branch (management service, not proxy). Grep `\.update_record(` to find remaining sites before trusting any "row update" code path in this repo.

**Also found + fixed: `_load_custom_rules` (shared/security/content_filter.py) used PyDAL-style query chaining `db(q1)(q2)`** — penguin_dal's `QuerySet` has no `__call__`, so this raised `TypeError: 'QuerySet' object is not callable`, caught and logged ("Failed to load custom rules"), silently returning `[]`. Net effect: org-scoped custom content-filter rules (including `action=block`) **never applied, ever**, regardless of DB config. Fixed by combining conditions with `&` before the single `db(combined).select()` call — the correct penguin_dal idiom (`Query.__and__` is supported; chained calls are not).

**Also found + fixed: `content_filter_audit_log.insert(..., timestamp=time.time())`** — the column is `Field("timestamp", "datetime", default=datetime.utcnow)`; penguin_dal rejects a raw float where SQLAlchemy expects a `datetime`, so every audit-log insert silently failed (caught, logged "Failed to log filter event"). No PII/injection filtering decision was ever actually audited. Fixed by dropping the kwarg and letting the field default apply.

**`get_db()` (shared/database/models.py) has a real, unfixed bug when called a second time against an already-migrated DB:** it hardcodes `reflect=True` (via `penguin_dal.DAL`'s default); against a sqlite/Postgres file that already has the schema, reflection populates `MetaData` with the existing tables, then `define_tables()` unconditionally tries `Table(name, metadata, ...)` again for all ~40 tables → `sqlalchemy.exc.InvalidRequestError: Table 'X' is already defined for this MetaData instance`. This would hit in production too on any second `get_db(migrate=False)` call in the same process against a pre-populated DB — not just a test artifact. Worked around in `tests/e2e/conftest.py._open_db()` via `DAL(url, migrate=False, reflect=False)` + `define_tables()` directly (bypassing `get_db()`); **not fixed at the source** — flagged as needing its own dedicated review since `get_db()` is the proxy's real startup path too.

**`cache_configs` table is Alembic-only** (`services/management/alembic/versions/009a_response_cache.py`), never `define_table()`'d in `shared/database/models.py`. Works in production via `get_db()`'s reflection against the shared Postgres DB (Alembic creates it, proxy's PyDAL layer reflects it). Cannot work under the `WADDLEAI_STUB_UPSTREAM=1` sqlite harness (`migrate=True`, no Alembic ever runs) — `CacheStage` 500s on `TableNotFoundError`. The two response-cache e2e tests are `@pytest.mark.skip`'d with this reason; fixtures (`cache_proxy`/`docker_redis`, which DOES work — verified real docker+redis container spin-up in this sandbox using a locally-cached `redis@sha256:...` digest, no network pull) are kept in conftest.py so the tests un-skip immediately once a Postgres+Alembic test tier exists.

**Also found, separately: enabling `waddleai.smart_routing` with zero `model_configs` rows silently rewrites `ctx.model` to the hardcoded default `"gpt-4"`** for any request (`RoutingEngine._pick_final`'s final fallback, shared/routing/engine.py) — not a bug exactly, but a footgun for any shared-process test fixture. And enabling `waddleai.proxy_memory` with no live Valkey makes `DedupStage` 500 unconditionally (`self.valkey.get()` with no None-guard, `shared/memory/token_len_cache.py`). Both are why `tests/e2e/conftest.py`'s default `proxy_process` fixture keeps every optional pipeline flag off and uses dedicated, isolated fixtures (`routing_proxy`) for the flows that need one on.

**Fixed real bug in `proxy/apps/proxy_server/main.py`'s `_build_pipeline`:** `valkey` was unconditionally reset to `None` whenever `_TEST_MODE` was true, even if `REDIS_URL` pointed at a real, successfully-constructed redis client — meaning the response-cache flag could never functionally work under `WADDLEAI_STUB_UPSTREAM=1`, full stop, regardless of infra. Fixed to only null it for `TokenBudgetStage`'s mock-limiter decision, not for the shared `valkey` variable `CacheStage`/`RoutingEngine` also read.

**Pre-existing, confirmed via `git stash` (not caused by this branch's changes):** `tests/contract/test_proxy_contract.py` has 6 failing tests (auth-matrix: bearer_jwt, xapikey_alone, raw_wa_key, bearer_wa_key, messages, messages_auth_xapikey_alone — all api-key/JWT related, likely downstream of the same `.update_record()`/auth class of bug, not fully root-caused). Also: `tests/integration/test_ollama_integration.py` has 3 failing tests (needs live Ollama, not properly skip-guarded). Also: `tests/smoke/` contains only `.sh` scripts (`test-production.sh`, `test_management_build.sh`), no pytest tests at all — `make smoke-test` runs `pytest tests/smoke` and will permanently fail (0 collected) until either real pytest smoke tests are added or the target is rewired to exec the shell scripts directly; this is a distinct, deeper issue than the `-d`-guard vacuous-pass fix applied to it.

**Makefile vacuous-pass fix:** `test-unit`/`test-integration`/`test-e2e`/`smoke-test` all had `@if [ -d tests/X ]; then pytest ...; fi` — if the directory were ever missing, the target exits 0 having run nothing. Removed the guard on all four (dirs are guaranteed by repo layout); added `--no-cov` to `test-integration`/`test-e2e`/`smoke-test` (mirroring `test-contract`'s existing convention) so a partial-tree pytest run isn't gated by the full-repo 60% `shared`+`services/management/app` coverage floor, which would otherwise mask a real "0 tests collected" failure behind a confusing coverage-percentage failure instead. `test-unit` intentionally keeps `--cov` (it's the target meant to enforce the floor).

**Environment gotcha for this sandbox specifically:** PATH's `python3` (`/home/penguin/.local/bin/python3`, a uv-managed 3.13 interpreter) has no project deps installed — no `.venv` exists in this worktree. `/usr/bin/python3` (3.12.3) has the full dependency set (pytest, quart, hypercorn, redis, etc.) and is what the task instructions specified for verification. `make test-e2e` etc. only work here via `PATH=/usr/bin:$PATH make test-e2e` — unrelated to any of the above fixes, a pre-existing local environment setup gap, not the Makefile's fault.
