**Resolved on `fix/smoke-tests`** (off `release/v0.2.X`): `make smoke-test` used to run `python3 -m pytest tests/smoke` guarded by `if [ -d tests/smoke ]; then ... fi` (vacuous-pass mask, same family as the 4 targets fixed on [[e2e-suite-and-penguin-dal-gotchas]]). `tests/smoke/` only ever had `.sh` scripts, never pytest — 0 collected = permanent failure once the mask was removed on `feature/e2e-suite`. Chose option (a): rewired `smoke-test` to `bash tests/smoke/test_management_build.sh` directly (file existence + full-tree `py_compile` syntax check + real `docker build` + requirements-package check, ~11-13s total, well under the 2min budget). `tests/smoke/test-production.sh` (hits a live prod URL with hardcoded `admin`/`admin123`) was split into a separate `smoke-test-production` target — needs live deployed infra + network, not appropriate for local/pre-commit.

**Found and fixed a second, independent masking bug inside the script itself**: `pass()`/`fail()` used `((TESTS_PASSED++))` under `set -e` — bash post-increment returns the *pre*-increment value as exit status, so `((0++))` returns 0/false on the very first call and `set -e` killed the script immediately after one `[PASS]` line. **This script had never once run to completion** — every prior "smoke tests passed" was actually zero tests having run past line 1, masked by the outer `if [ -d ]` always exiting 0 regardless. Fixed with `: $((TESTS_PASSED++))` (`:` always exits 0). Also removed the stale Test 4 (docker-compose config check — docker-compose is house-deprecated, no `docker-compose.yml` exists in this repo anymore) and rewrote Test 2's hardcoded per-file list (referenced a since-removed `app/api/v1/ailb.py`) as a `find`-driven loop over `shared/` + `services/management/app/` so it can't go stale the same way again. Test 5's package checks (`flask`, `flask-security-too`, `pydal`) were checking a stack this service migrated off of — replaced with `quart`, `penguin-aaa`, `penguin-dal`, `grpcio` (the actual `requirements.in` direct deps).

**Discovered but NOT fixed (out of scope for tests/smoke/, flagging per house "never ignore pre-existing failures" rule):** actually running the built management image (`docker run` with `DB_TYPE=sqlite`, no redis) crashes on boot — `ModuleNotFoundError: No module named 'orjson'`, raised importing `services/management/app/api/v1/cache_configs.py` → `shared/cache/config.py` → `import orjson`. `orjson` is not declared in `services/management/requirements.in`/`.txt` at all (not even transitively). This is invisible to `python3 -m py_compile` (no import execution) and to `docker build` (installs declared deps, doesn't run the app) — only a real container **run** step catches it, which is why it was never caught. Whoever owns `services/management/requirements.in` needs to add `orjson` and recompile with `uv pip compile --generate-hashes`. Related: [[e2e-suite-and-penguin-dal-gotchas]] already flags `cache_configs` as Alembic-only/unreachable under the sqlite e2e harness — this is a distinct, more fundamental import-time bug (missing pin), not the same issue.
