Fixed in `fix/proxy-telemetry-and-bounds` -> release/v0.2.X PR #267 (2026-10-03):

- **`request.url_rule.rule` for the `endpoint` metric label, not `request.path`** — Quart's `request.url_rule` is `None` only when no route matched (404/405); fall back to the literal `unmatched`. `_sanitize_label()` in `shared/utils/metrics.py` is a defensive-only backstop (UUID/2+-digit-numeric path segment -> `<id>`), not the primary fix.
- **Quart's test client does NOT set `Content-Length` for its `json=` kwarg** — a `MAX_CONTENT_LENGTH`/413 test must build a raw `data=` payload with an explicit `Content-Length` header, or the lazy Werkzeug enforcement never fires and the handler's own broad `except Exception` swallows nothing (because nothing was ever raised).
- **A route's own `except Exception` around `request.get_json()` swallows `RequestEntityTooLarge`**, converting a would-be 413 into a generic 500 before any `@app.errorhandler` ever sees it. Fix: a `before_request` hook that checks the `Content-Length` header and `abort(413)` *before* routing/dispatch — runs strictly before the view function, so the broad except never gets a chance. Caveat: a request with no Content-Length header (true chunked transfer) isn't covered by this early check; Werkzeug's lazy body-read enforcement is the remaining backstop for that case, but it'll still get swallowed by a route's broad except — known residual gap, documented, not fixed (would require editing files owned by sibling agents mid-rewrite).
- **`mem0_bp` blueprint is mounted at `url_prefix="/mem0"`** — the real route is `/mem0/memories/<memory_id>`, not `/memories/<memory_id>`. Easy to get wrong when picking a parametrized route for an endpoint-label test.
- **`OIDCAuthMiddleware` intercepts before Quart routing** — an unauthenticated request to a genuinely nonexistent path returns 401, not 404; a 404-fallback test needs a valid bearer token to actually reach Quart's own routing/404 logic.
- **`TokenLimiter.valkey`** is the real attribute to inspect when proving a `redis.from_url(...)` call site used bounded pool kwargs — reachable via `pipeline.stages[i].token_limiter.valkey` after forcing `_TEST_MODE = False` + a resolvable `REDIS_URL` and calling `proxy_server._build_pipeline()` directly (same technique as the pre-existing `test_non_test_mode_uses_real_metering_buffer`). The `ProxyServer.startup()` memory-layer `redis.from_url` call site isn't independently re-exercisable without a full second server boot — accepted as reviewed-by-symmetry (same shared `_valkey_client_kwargs()` helper) rather than forcing a heavyweight test.
- Fresh isolated venv recipe that actually works for this repo: python**3.13** (not 3.12 — `penguin-sal==0.2.1` requires >=3.13) venv, install `proxy/requirements.txt` (NOT the root `requirements.txt`, which omits `quart` entirely), then `pip install pytest-cov` (absent from every requirements file). `/usr/bin/python3` (3.12, system-site-packages) has stale `penguin_dal==0.1.0`/missing `supabase` — don't use it for proxy tests.
- **No new PostHog kill-switch flag added** for these fixes — judgment call: these are hardening/bug fixes to already-enforced mechanisms (the pre-existing `ConcurrencyLimiter` itself shipped in an earlier audit PR without one), not new user-facing behavior. Documented the reasoning explicitly in the PR body rather than silently skip it.
- Coverage ratchet: touching `shared/utils/metrics.py` for 3 new methods meant bringing the WHOLE file to ≥90% (COMMON.md: "measure coverage of every module you touched"), not just the new lines — ended up writing direct unit tests for ~15 pre-existing-but-previously-untested methods (hook metrics, record_database_operation, MetricsMiddleware, get_management_metrics/get_metrics_for_service) to go from 65% to 98%.
